# เลขทะเบียนคำขอ ว119

## พฤติกรรม

- ใช้ `W119-001`, `W119-002`, … แยกจาก POL-01 เป็นเลขต่อเนื่องทั้งระบบ ไม่รีเซ็ตตามปีงบประมาณ
- จองเลขเมื่อฐานข้อมูลสร้างฉบับร่างสำเร็จ ไม่จองเมื่อเปิดหน้า/เปิดตัวอย่าง การแก้ไขหรือส่งใหม่ใช้ UUID และเลขเดิม
- เลขอย่างน้อย 3 หลัก แต่ไม่ตัดหลักพัน (`W119-1000`) ใช้ PostgreSQL sequence และ unique constraint ไม่ใช้การนับจำนวนแถวในหน้าเว็บ
- เลขอาจข้ามเมื่อ transaction ล้มเหลว/มีการลบคำขอ ไม่ย้อนตัวนับหรือเอาเลขเก่ากลับมาใช้
- เปลี่ยนเฉพาะคำขอ `form_data.formType = 'w119'` เดิม ตาม `created_at, id` จากเก่าไปใหม่ ทุกสถานะรวมฉบับร่าง หากมีเลข W119 อยู่แล้ว ให้คงไว้และจัดเลขที่เหลือต่อจากค่าสูงสุด
- `form_data.documentNo` (เลขหนังสือราชการในช่อง “ที่”) ไม่ใช่เลขทะเบียน และไม่เปลี่ยน
- เลขปัจจุบันปรากฏในทะเบียน หน้ารายละเอียด ตัวอย่างที่บันทึกแล้ว และท้าย PDF; ชื่อไฟล์ใหม่เป็น `W119-001.pdf` ไม่เติม W119 ซ้ำ
- หน้ารายละเอียดแสดงเลขเดิม ลิงก์รายละเอียด/แก้ไข/พิมพ์ด้วยเลขเก่ายังเปิด UUID เดิมได้; ปุ่มในหน้าที่เปิดใช้เลขปัจจุบัน การค้นหาในทะเบียนคำขอและทะเบียนเบิกจ่ายรองรับเลขเดิมด้วย
- ไฟล์ PDF ที่เคยดาวน์โหลดหรือแนบไว้แล้วไม่ถูกแก้ทับ เอกสารเก่ายังอ้างอิงเลขเดิมได้ผ่านทะเบียนประวัติ การสร้าง PDF ใหม่ใช้เลขปัจจุบัน
- ไม่แก้ประวัติอนุมัติ ข้อความบันทึกเดิม รายการพัสดุ เอกสารแนบ หรือ foreign key ของคำขอเบิกจ่าย

## ลำดับนำขึ้นระบบ (ต้องแยกสอง migration)

ยังไม่ได้รันกับ production ในงานพัฒนานี้ ห้ามรันทั้งสอง migration ก่อนนำโค้ดใหม่ขึ้น เพราะแอปรุ่นเก่าไม่รู้จักลิงก์เลขเดิม

1. สำรองฐานข้อมูลและส่งออก `id, request_no, created_at, status, form_data` ของคำขอ ว119 รวมถึงค่าตัวนับ POL01 เก็บในที่ปลอดภัย ตรวจจำนวนเอกสารและชนิดฟอร์มกับเจ้าหน้าที่
2. รันเฉพาะ `202610140001_request_number_aliases.sql` เพื่อเตรียมตารางประวัติ RPC และ view โดยยังไม่เปลี่ยนเลขใด ๆ แอปรุ่นเดิมยังใช้งานได้
3. Deploy โค้ดชุดนี้ แล้วตรวจรายละเอียด/แก้ไข/พิมพ์คำขอเลข POL01 เดิมให้ทำงานกับ RPC ใหม่ได้จริง
4. รัน `202610140002_w119_request_numbering.sql` ช่วงใช้งานน้อย การเปลี่ยนเลข/บันทึกประวัติอยู่ใน transaction เดียว และล็อกการเขียนตารางคำขอระหว่างจัดเลข
5. ตรวจจำนวนก่อน–หลัง คู่เลขเก่า–ใหม่ UUID เอกสารแนบ และคำขอเบิกจ่าย แล้วเปิดเลขเก่าและใหม่ ตรวจ PDF ของคำขอจริงโดยไม่สร้างคำขอทดสอบใน production

ตัวอย่าง read-only สำหรับตรวจผล (ผู้ดูแลฐานข้อมูล):

```sql
select a.old_request_no, r.request_no, r.id, r.status, a.changed_at
from public.request_number_aliases a
join public.procurement_requests r on r.id = a.request_id
order by r.created_at, r.id;

select count(*) as remaining_legacy_w119
from public.procurement_requests
where form_data->>'formType' = 'w119' and request_no !~ '^W119-[0-9]+$';

select last_value, is_called from public.w119_request_no_seq;
```

หลัง activation **อย่า rollback แอปเป็นรุ่นที่ไม่รองรับ alias** และอย่าลบตารางประวัติ/ลดตัวนับ หากต้องแก้ปัญหาให้คงโค้ด resolver ไว้และแก้เดินหน้า การคืนเลขเดิมต้องเป็นงานซ่อมข้อมูลแยกที่ได้รับอนุมัติ พร้อมสำรองคู่เลขก่อนดำเนินการ

## ขอบเขตทดสอบ

`npm run test:sql` รวมชุด `w119-numbering.mjs`: ใช้ฐานข้อมูล PGlite แยกพร้อมข้อมูลจำลอง ตรวจ migration ซ้ำ, RPC สร้างคำขอจริง, ตัวนับแยก, หลักพัน, UUID/ข้อมูลเกี่ยวข้องไม่เปลี่ยน, การค้นหาเลขเดิม, เจ้าของ/ผู้อื่น/ผู้ดูแล/anonymous และสิทธิ์ read-only ของ alias

PGlite ทำงานบน connection เดียว แม้ทดสอบเรียกหลายครั้งพร้อมกัน จึงไม่ใช่การทดสอบโหลดแบบหลาย connection; การกันเลขซ้ำอาศัย atomic sequence และ unique constraint ของ PostgreSQL ต้องตรวจ staging/Supabase เพิ่มก่อน activation

Unit tests ตรวจรายละเอียด/ลิงก์แก้ไขผ่านเลขเก่า, fail-closed เมื่อค้นหาตัวตนไม่ได้, การคงเงื่อนไขเจ้าของ/สถานะ, ตัวอย่างที่ยังไม่บันทึกไม่มีเลขสมมติ และชื่อไฟล์/เลขใน PDF
